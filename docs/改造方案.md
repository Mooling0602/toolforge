# ToolForge 改造方案（完整版）

> 目标：做成一个**干净、可 Docker / 本地运行的通用工具调用中间件**。  
> 能力来源：**qwen2API 的工具调用引擎** + **Toolify 的中间件形态**，取长补短，合并成一份产品。

---

## 一、你现在为什么觉得「怪 / 丑 / 看不懂」

当前仓库是「边做边堆」出来的，不是按产品形态设计的：

| 现状 | 问题 |
|------|------|
| `vendor/xyml-toolcall` | 把解析引擎当**另一个 pip 包**嵌进来。逻辑上它就是中间件的一部分，不该像外来依赖一样躺在 vendor 里。 |
| `src/toolforge/...` 过深 | `fc/` `engine/` `protocols/` `stream/` `upstream/` 切太碎，新人分不清从哪进。 |
| `tests/` 很多 | 开发期防回归用的，**不是产品功能**。可以保留，但不应让你误以为要「部署测试」。 |
| README 写多了演进史 | Phase1/2/3、相关项目对比，干扰「怎么用」。 |
| 和 Toolify / qwen2API 的关系说不清 | 看起来像山寨两套，而不是**合并后的一个中间件**。 |

**结论：功能方向对，目录形态错。要做的是「产品化重构」，不是再堆功能。**

---

## 二、两个源头各自是什么

### 1. Toolify（通用中间件形态）

- 定位：**夹在客户端和任意 LLM 之间的代理**
- 流程：拦截带 `tools` 的请求 → 注入提示词 → 上游当普通聊天 → 解析文本 → 返回标准 `tool_calls`
- 强项：
  - 给**任意** OpenAI 兼容 API 补 FC
  - 配置多上游、鉴权、Docker 部署
  - 产品形态清晰：`Client → Middleware → LLM`
- 弱项：
  - 解析栈相对简单（XML + trigger）
  - 协议面主要是 OpenAI Chat
  - 无 qwen2API 那套容错/流式 sieve/CLI 画像

### 2. qwen2API（你写的工具调用能力）

- 定位：**千问 Web → 多协议 API 的网关**，工具调用是其中一块
- 强项（应完整带走）：
  - 多格式解析：XYML / QNML / XML / JSON / text-KV
  - 流式 `ToolSieve`（半包 marker 不泄漏）
  - 参数 coerce、去重、截断恢复
  - 工具名别名 / 可选混淆（Read ↔ fs_open_file）
  - CLI profile（Claude Code / Hermes / OpenClaw / OpenCode）
  - 出口：OpenAI `tool_calls` / Anthropic `tool_use` / Responses `function_call`
  - 历史回灌：assistant tool_calls ↔ markup；tool result ↔ 文本
- 弱项（中间件里不要带）：
  - 绑死千问 Web / 账号池 / OSS / Playwright / WebUI
  - 和网关运行时缠在一起

### 3. 合并后的产品（ToolForge 应成为的样子）

```text
任意客户端（OpenAI / Anthropic / Gemini SDK）
        │  标准 tools / tool_calls / tool_use / functionCall
        ▼
┌───────────────────────────────────────┐
│  ToolForge（本仓库）                  │
│  · 鉴权 / 多上游路由                  │  ← Toolify 形态
│  · 原生 FC 透传 或 提示词 FC          │  ← 两边都有，合并策略
│  · XYML 引擎 + 流式 sieve + 恢复      │  ← qwen2API 能力
│  · 多协议入出                         │  ← 比 Toolify 更全
└───────────────────────────────────────┘
        │
        ▼
任意上游：OpenAI / Anthropic / Gemini / Grok / 本地 OpenAI 兼容 / qwen2API 当上游
```

**一句话：Toolify 的「壳」+ qwen2API 的「工具调用芯」。**

## 三、能力对照：谁有什么、怎么合

| 能力 | Toolify | qwen2API | 合并后 ToolForge |
|------|---------|----------|------------------|
| 独立中间件代理 | ✅ | ❌（绑网关） | ✅ 必须 |
| 任意 OpenAI 兼容上游 | ✅ | ❌ | ✅ |
| 配置多上游 + Key | ✅ | 账号池（另一套） | ✅ YAML 多上游 |
| Docker 一键起 | ✅ | ✅（整站） | ✅ 只要中间件 |
| 提示词诱导 FC | ✅（XML） | ✅（QNML/XYML 更强） | ✅ 用 XYML 引擎 |
| 原生 FC 透传 | 可选/弱 | 上游固定 tool_choice none 偏 prompt | ✅ auto：有则透传，无则 prompt |
| 多格式解析 | 弱 | 强 | ✅ 迁入引擎，**内联进项目** |
| 流式 tool 分离 | 有 | sieve 更稳 | ✅ |
| 截断/解析重试 | 有 | 有 | ✅ |
| CLI profile / few-shot | ❌ | ✅ | ✅ 可开关 |
| 名称混淆 | ❌ | ✅ | ✅ 可开关 |
| OpenAI Chat 入出 | ✅ | ✅ | ✅ |
| Anthropic Messages | 弱/无 | ✅ | ✅ |
| Gemini | 弱/无 | 部分 | ✅ |
| OpenAI Responses + 真 SSE | ❌ | 有出口 | ✅ |
| 执行工具 | ❌（客户端） | ❌（客户端） | ❌ 永不执行 |
| 千问账号池/WebUI | ❌ | ✅ | ❌ 不进本仓库 |

### Toolify 有、qwen2API 中间件形态缺的

1. **独立中间件产品边界**（只做 FC，不当 2API 网关）  
2. **任意上游路由**（model → base_url）  
3. **给别人用的部署姿势**（config.yaml + Docker + client key）  
4. **「不会 FC 的模型也能用 tools」的明确卖点**

### qwen2API 有、Toolify 缺的

1. **XYML/QNML 等强解析 + coerce**  
2. **流式 sieve**  
3. **截断恢复 / 交付过滤思路**  
4. **CLI 工具名画像**  
5. **多协议客户端出口**  
6. **工具历史渲染**（第二轮 tool result 回灌质量）

## 四、目标目录（改造后应长这样）

砍掉「包中包」和「看不懂的分层名词」，改成**一个中间件服务**：

```text
toolforge/
├── README.md                 # 只用：是什么、Docker、本地、配置、端点
├── docs/
│   └── 改造方案.md           # 本文件
├── Dockerfile
├── docker-compose.yml
├── config.example.yaml
├── requirements.txt          # 运行依赖（简单）
├── app/                      # 全部业务代码（不要再 src/toolforge 套娃）
│   ├── __init__.py
│   ├── main.py               # FastAPI 入口 + 路由（唯一入口）
│   ├── config.py
│   ├── auth.py
│   ├── models.py             # Canonical 请求/响应
│   ├── engine/               # ★ 工具调用核心（原 qwen 能力内联）
│   │   ├── __init__.py
│   │   ├── xyml.py           # 原 xyml-toolcall/core：parse/render/sieve
│   │   ├── policy.py         # native vs prompt
│   │   ├── inject.py         # 指令注入 + 历史
│   │   ├── parse_out.py      # 出口 OpenAI/Anthropic/Gemini
│   │   ├── recovery.py
│   │   └── profiles.py
│   ├── adapters/             # 客户端协议 ↔ 内部模型
│   │   ├── openai_chat.py
│   │   ├── openai_responses.py
│   │   ├── anthropic.py
│   │   └── gemini.py
│   ├── upstream/             # 上游 HTTP
│   │   ├── openai.py
│   │   ├── anthropic.py
│   │   └── gemini.py
│   ├── stream.py             # SSE 公共 + Chat/Responses 流式
│   └── pipeline.py           # 一次请求的总编排（原 orchestrator）
├── tests/                    # 可选；CI 用，部署不需要
└── examples/
    └── e2e_live.py           # 可选联调
```

### 明确删除 / 合并的

| 现状 | 改造 |
|------|------|
| `vendor/xyml-toolcall/` | **内联进 `app/engine/xyml.py`**，不再当独立包 |
| `src/toolforge/` | 改名为扁平 `app/` |
| `fc/` + `engine/` + `stream/` 交叉 | 收敛：`engine/` + `stream.py` + `pipeline.py` |
| `packages` 式 pyproject 复杂依赖 | `requirements.txt` + 简单 `pyproject` 可选 |
| README 相关项目 / Phase 历史 | 删光，只留用法 |
| 无用 Protocol 空壳、重复 re-export | 删 |

**为什么不要 vendor：**  
vendor 是「临时借用别人包」的姿势。XYML 引擎是**本中间件的心脏**，应是 `app/engine` 的一部分。用户打开仓库只应看到「一个中间件」，而不是「中间件 + 嵌套 SDK」。

## 五、运行形态（改造后）

### Docker

```bash
cp config.example.yaml config.yaml   # 改上游
docker compose up -d --build
curl http://127.0.0.1:8080/healthz
```

### 本地

```bash
python -m venv .venv && source .venv/bin/activate  # Windows 用 Scripts\activate
pip install -r requirements.txt
uvicorn app.main:app --host 0.0.0.0 --port 8080
```

### 客户端

```text
base_url = http://127.0.0.1:8080/v1
api_key  = config 里 allowed_keys
正常传 tools → 拿 tool_calls
```

## 六、核心请求路径（改造后逻辑不变、代码变清晰）

```text
1. 鉴权
2. 协议入站 → CanonicalRequest（messages + tools + stream）
3. 按 model 选上游
4. 决策：
   - 无 tools → 纯透传
   - native_fc → Path A 带 tools 转发
   - 否则 Path B：inject XYML + 剥 tools → 上游纯文本
5. 响应：
   - Path A：映射为客户端协议
   - Path B：sieve/parse → 标准 tool 结构
6. 流式：统一 SSE 出口（Chat / Responses / Anthropic）
7. 永不执行工具
```

## 七、改造任务清单（按顺序做）

### 阶段 A — 目录与依赖（先让仓库「像产品」）

1. 新建 `app/` 扁平结构  
2. 将 `vendor/xyml-toolcall/src/xyml_toolcall/core.py` **迁入** `app/engine/xyml.py`，改 import，**删除 vendor/**  
3. 合并 `src/toolforge/**` → `app/**`，去掉 `src/`  
4. `requirements.txt`：fastapi uvicorn httpx pyyaml  
5. Dockerfile / compose 改为 `uvicorn app.main:app`  
6. README 只保留：是什么 / Docker / 本地 / 配置 / 端点  

### 阶段 B — 代码收敛（减少文件、统一入口）

7. 单一 `app/main.py` 挂所有路由  
8. `pipeline.py` 统一编排，删除重复 stream 路径  
9. adapters 只负责「协议 ↔ Canonical」  
10. 配置字段保持兼容 `config.example.yaml`  

### 阶段 C — 验证

11. 本地：`uvicorn` + mock 上游 / 现有单测迁移到 `tests/`  
12. Docker build & healthz  
13. 可选：e2e 打真上游一轮 Chat 流式 + tool_calls  

### 阶段 D — 提交

14. 推送到 `YuJunZhiXue/toolforge`  

**不做的事：**

- 不搬 qwen2API 账号池、WebUI、图片/视频、Playwright  
- 不 fork Toolify 源码（GPL），只保留形态  
- 不把中间件做成「执行工具的 Agent」

## 八、配置最终形态（示例）

```yaml
server:
  host: "0.0.0.0"
  port: 8080

client_authentication:
  enabled: true
  allowed_keys: ["sk-toolforge-demo"]

upstreams:
  - name: local
    type: openai_compat
    base_url: "http://host.docker.internal:7860/v1"  # 可指你的 qwen2API
    api_key: "sk-xxx"
    models: ["*"]
    native_fc: false    # qwen2API 当上游时常用 prompt 路径
    is_default: true

features:
  fc_mode: auto
  enable_streaming: true
  inject_protocol: XYML
```

- 上游是 **真 OpenAI/Claude 且支持 tools** → `native_fc: true`  
- 上游是 **本地小模型 / 不完整兼容 / qwen 网关** → `native_fc: false`
